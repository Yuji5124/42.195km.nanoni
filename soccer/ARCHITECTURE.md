# サッカー、なのに。 — 設計（Vertical Slice）

**「10 万人の中から自分の席を探していたら、90 分のサッカーが全部終わった。」**

機能を足すかどうかは「この一文を面白くするか？」で決める。
今回の範囲は **3〜4 分の Vertical Slice = 前半 45 分**。後半・ハーフタイムの空席激増・望遠鏡・AI Seat Detector は次の段階。

## 他のモードに影響しないための形

- `soccer/` は独立したページ（`vite.config.js` の入力 `soccer`）。`src/` の部品（`AudioManager` / `RunnerModel` / `Particles` / `textures.js` / `math.js` / `EventBus`）を **読み込むだけ**
- `src/` への変更は追加だけ: `src/core/Game.js` の `EXTERNAL` に `soccer` を 1 行、`index.html` にカードを 1 枚
- 依存パッケージは増やしていない（`three` と `vite` のみ）。画像・音声ファイルも無し（Canvas と WebAudio で生成）

## スタジアム（10 万席）

- 角丸長方形のボウル 2 層。コア長方形（80 × 46m）からの距離 `R0 + d` の線が座席の列。直線部の長さは `d` によらず角の円弧だけ伸びる → **ブロックの境目（通路）は放射状にそろう**
- 下層 LOWER: 34 列・32 ブロック（1〜32）/ 上層 UPPER: 56 列・64 ブロック（33〜96、傾斜 36°）
- 自然に並べると 100,624 席 → 南上層の中央（大型ビジョンの下の放送ブース）を最上段から座席なしにして **ちょうど 100,000**
- 座標: ピッチ中心が原点、NORTH = +X。ブロック 42 が北の中央。ループ位置 `s`（北の中央 = 0 → 東 → 南 → 西）
- 1 回目のプレイの席は **BLOCK 42 · ROW 19 · SEAT 5**（42.195）。2 回目からは seed で上層のどこか（大型ビジョンで隠れない列）

### 画面の点 → 座席（three-mesh-bvh は使わない）

各層の「胸の高さの面」とレイの交点を粗い刻み（0.8m）+ 二分法で求め、`(x, z) → (d, s)` を解析的に逆算して列と座席を二分探索する。
**1 回 0.06〜0.08ms**（Node）。three.js の `InstancedMesh(10 万).raycast` は **8.5ms**（全インスタンスの総当たり）。BVH を作るまでもなく、座席が規則的な格子であることを使う方が速い。

## 観客（論理 100,000 人・毎フレームの JS は 96 ブロックぶんだけ）

| LOD | 範囲 | 描き方 |
| --- | --- | --- |
| FAR | 座席が画面で 2.5px 未満 | ビルボードを 2 色のかたまりに（服 / 頭）。最低 1.4px の幅を保証 → 抜け・ちらつきが出ない |
| MID | それ以上（双眼鏡の中など） | 同じビルボードのシェーダーで形を描く: 頭・髪・胴・腕（上げる / 拍手 / スマホ）・マフラー（首 / 両手で掲げる）・日の丸の小旗・背番号。MSAA + alpha-to-coverage で縁が滑らか（半透明のソート不要） |
| NEAR | 主人公から 30m・最大 1500 人（画質で 320〜1500） | `RunnerModel` のローポリ人型（96 tris）を 1 draw call。座ると脚を前へ曲げる。その席のビルボードは `iMeta.x += 128` で消す |
| VERY NEAR | 1〜2 人 | 通路で旗を振る人・前の席の人。姿勢を CPU から上書き（`iOver`） |

- 属性は 1 人 24 バイト: `iPos`（x y z s: Float32 × 4）/ `iLook`（服 | 髪, 肌 | 小物, r1, r2: Uint8 × 4）/ `iMeta`（kind, block, row: Uint8 × 4）
- 姿勢 = ブロックの「前の姿勢 → 次の姿勢」+ 切り替え時刻 + ばらつき（DataTexture 128 × 3）。1 人 1 人は `r1`（遅れ）・`r2`（速さ・どこまで立つか・身長）で少しずつ違う → **「大きな集団として動き、その中に個体差がある」**
- 何もない時も数秒ごとに約 2% の人が手を上げる・立つ（静止画に見せない）
- ウェーブ: `s` の上を動くガウスの山（uniform 1 つ）。一周 22 秒
- 同じ式を CPU にも持つ（`CrowdDirector.poseAt`）: 「前の人が立っていて見えない」「ウェーブで見えない」の判定に使う
- 近くの人形と遠くのビルボードは同じ DataTexture を読むので、立ち上がるタイミングがそろう

### 群衆の描き方の実測比較（10 万人・960 × 540・SwiftShader）

GitHub の Actions / このコンテナには GPU が無いので、Chromium の SwiftShader（CPU で描く WebGL）で測った。**絶対値は実機と無関係、相対比較のみ**。視点はゲームと同じ（南下層から北を見る）。

| 方式 | 三角形 | CPU（render の呼び出し） | 1 フレーム |
| --- | --- | --- | --- |
| **ビルボード（採用）** | 200k | 0.76ms | 1,122ms |
| `THREE.InstancedMesh`（96 tris × 10 万） | 9.6M | 0.57ms | 3,538ms |
| `THREE.BatchedMesh`（インスタンスごとの CPU カリング） | 4.4M | 23.1ms | 2,465ms |
| `InstancedMesh2`（@three.ez/instanced-mesh 0.3.16） | 4.4M | 7.5ms | 2,352ms |
| 同 + `computeBVH()` | 4.4M | 5.1ms（構築 173ms） | 2,568ms |
| `THREE.Points`（1 色の点） | 0 | 0.15ms | 43ms |

- 3D の人形を 10 万並べると、カリングしても 440 万三角形。iPhone の 30fps には重すぎる
- InstancedMesh2 / BatchedMesh は **CPU で 10 万インスタンスをカリング**するので、PC でも 5〜23ms。iPhone では CPU の予算（33ms）をそれだけで使い切る
- Points は最速だが、人の形・腕・マフラー・立ち上がりを表せない（点の最大サイズの制限もある）
- → 10 万人は「頂点 4 つのビルボード + GPU で姿勢」。3D の人形は近くの 1500 人だけ

## 席探し（公平性）

- 見た目は 10 万席から 1 席。本物の空席は **いつも 1 つ**（`kind = 1`）。空席っぽく見えるデコイは全体の約 0.6%（約 600）
  - トイレ・売店の人の席（調べると数秒後に戻ってくる）/ 荷物 / 子供 / 座席と同じ色の服で寝ている人
  - 本物のすぐ隣（前後 1 列・左右数席）にはデコイを置かない
- 座席はターコイズ色。人が座っていれば背もたれは肩に隠れ、空いていれば背もたれ（頭の無いターコイズのかたまり）が見える
- **調べる**: 座席が画面で 2.6px 未満なら「遠すぎて見えない」（肉眼で反対側は調べられない → 双眼鏡が要る）。
  指の下の数席の中から「空席っぽく見えて、今見えている席」を優先（指より細かい精度を求めない）。前の人が立っている・ウェーブが通過中なら見えない
- **ヒント**（段階的に絞る。正解の位置を矢印で出さない）:
  `100,000 → UPPER 70,464 → NORTH 17,744 → BLOCK 4? 11,108 → ROW 1? 1,774`
  隣の客（チケットの色）→ 場内放送（北ゲート）→ 大型ビジョンの CROWD CAM → 隣の客（にじんだ列）。
  ブロック番号は上層の手すり壁・最上段の壁、列番号は通路の階段に書いてある（双眼鏡で読める）
- **進展がない時のヒント**（40 秒）: 双眼鏡の使い方 / 場内放送でブロックの十の位 / 列番号の場所 / 背もたれの色
- 4 分 20 秒を過ぎても見つからなければ係員が案内する（必ず前半の終わりに座れる）

## 試合（MatchDirector）

- 90 分を 9 倍速再生しない。**選手とボールはいつも普通の速さ**（ジョグ 3.5m/s・スプリント 7.8m/s・パス 12〜22m/s・シュート 26m/s）。時計だけが速い（前半 45 分 = 実時間 228 秒）
- 見せ場の表（`data/timeline.js` の MOMENTS: シュートの時刻・チーム・結果・最後のボール）から、**攻撃の組み立てを逆算して始める**（パス 3 本 → クロス / スルーパス / コーナー / ミドル → シュート）。持つ時間を伸び縮みさせて時刻に合わせる
- 見せ場の間はつなぎのポゼッション（最後はパスカットで攻守交代）。ゴールの後は喜ぶ → 自陣へ戻る → キックオフ（場面転換）
- 選手は「チームの形（ボールに寄る・押し上げる・下がる）」+「役目（受け手は落下点へ・キーパーは正面 / 逆へ跳ぶ）」だけ。22 人を AI にしない
- 見つけて移動している間の見せ場は、試合側では起こさず **音だけ**で起きて結果に数える（「移動中に 2 点入った」）

## 大型ビジョン

- 中継カメラ（西スタンドの上からボールを追う）を RenderTarget（HIGH 640 × 328 → VERY LOW 320 × 164）に描いて、北と南の画面に貼る。更新は画質で毎フレーム〜4 フレームに 1 回
- 10 万人も中継に映す（中継カメラ用に `uPxScale` を差し替えるので遠景 LOD が効いて軽い）。近くの 3D 観客・旗・紙吹雪は layer 1 にして中継には映さない
- 重ね（Canvas 640 × 328）: スコア・時計・LIVE / REPLAY / CROWD CAM・実況字幕・巨大な文字・広告・ADDITIONAL TIME

## 流れ

- **オープニング（約 31 秒・スキップ可）**: 黒画面に KICK OFF 19:00 → 19:00:01 → スマホ MATCH STARTED →「間に合った。」→ QR ゲート ERROR × 2 → 裏返して OPEN → 暗いトンネルの奥の光 → 外へ出ると一気に開けた 10 万人 →「100,000」→ キックオフ → チケットの座席だけにじんでいる → 係員「お客様のお席だけ、空いております。」「どこですか？」「分かりません。」→ タイトル
- **探索**: 肉眼（0:00〜）→ 双眼鏡（0:46 隣の客「使います？」4〜8 倍）→ ヒント → ゴール（1:52「見えない。」）→ 失点 → 決定機 → 追加点 → 45 分
- **YOUR SEAT FOUND** → 「……反対側だ。」→ **移動**（トンネルへ入る。連打で急ぐ。歓声がこもって聞こえる。時計は 45 分へ早送り）
- **着席**: 「やっと見られる。」→ 実況「前半、最後のワンプレー！」→ シュートの瞬間に前の席の人が立ち上がる →「えっ」→ ゴール → ピッピッピーーー → **HALF TIME** →「すごい前半だった！」「歴史に残るな、これは！」→「……。」
- **結果**: MATCH TIME / REAL PLAY TIME / MATCH WATCHED（ボールが画面の中央付近にあって遮られていなかった時間）/ GOALS / GOALS ACTUALLY SEEN / SEATS / SEATS CHECKED / FALSE ALARMS / YOUR SEAT / FOUND BY

## 音（WebAudio で合成）

- `stadium` バス → こもりフィルタ（トンネル・移動中は 420Hz まで閉じる）→ master
- ざわめき（低い帯 + 高い帯のノイズ）と、盛り上がり（立っている人の割合）で開くうねり
- 声 = のこぎり波 × 6〜8 をフォルマント 2 本に通す（「オー」「アー」「ウー」）。チャント「ニッ・ポン！（チャ・チャ・チャ）」、アウェイ席のサンバの太鼓
- ゴール: ノイズの山 + 声 + 低音 + ホーン → 長い拍手。決定機は「オォ…」上がり、外れは「アァ…」下がる。アウェイのゴールはブーイング
- 笛（短い / 長い / ピッピッピーーー）・場内放送のチャイム（ピンポンパーン）・スマホ・QR ゲート・双眼鏡のモーター・調べる音

## スマートフォン（iPhone Safari）

- Pointer Events で指とマウスを同じに扱う。`setPointerCapture`、`pointercancel` / `lostpointercapture` / `blur` / `visibilitychange` で全部の指を離したことにする
- CSS `touch-action: none` + `gesturestart` の既定動作を止める（ページの拡大を防ぐ）、`user-scalable=no`、`-webkit-touch-callout: none`
- ドラッグは「つかんで動かす」（Street View と同じ向き）。ドラッグ 1px = 画面上の 1px ぶん回る（双眼鏡でも指に吸い付く）
- 双眼鏡のボタン・候補 A B C は親指の届く下の角。`env(safe-area-inset-*)` で切り欠きを避ける。横長の低い画面は下の余白を詰める
- 縦長でも横の見える幅（約 44°）を保つよう縦の画角を広げる（52〜78°）
- 音: 最初の `pointerdown` / `pointerup` / `touchend` で AudioContext を作り直し・再開（Howler.js と同じ考え方）
- 画面を隠すと一時停止。向きの変更は 250ms 後にもう一度サイズを取り直す

## パフォーマンス

- **Performance Governor**: HIGH（PC の初期値）/ MEDIUM（タッチ端末の初期値）/ LOW / VERY LOW。1 秒ごとに FPS を測り、目標（PC 52 / タッチ 40）を 3 秒続けて下回ったら 1 段下げる。十分速ければ 10 秒後に 1 段上げる（1 回まで）
  - 変える: pixelRatio（2 / 1.5 / 1.15 / 0.85）・近くの 3D 観客（1500 / 1000 / 600 / 320）・ビジョンの解像度と更新頻度・alpha-to-coverage・紙吹雪
  - 変えない: **観客 100,000 人**
- 測定（`?debug` の開発パネル。SwiftShader の値。FPS 以外は実機でも同じ）:
  - JS（毎フレームの update 全部）**約 0.2ms**、観客の更新 0.001ms 未満、ピック 0.06ms
  - draw call: 主画面 約 35〜40 + ビジョン 約 20 = **50〜60**
  - 三角形: 観客ビルボード 200k + 近くの人形 最大 144k + スタンド等 → 主画面 約 45 万、ビジョンを毎フレーム描く HIGH で合計 約 72 万
- 主なボトルネック（予想）: 10 万ビルボードのフラグメント（discard + MSAA）と、ビジョンの 2 回目の描画。前者は遠景の 2 色 LOD と pixelRatio、後者は更新頻度で調整する
